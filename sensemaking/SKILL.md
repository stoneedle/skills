# 业务上下文

将业务知识维护作为业务工作的必经步骤。用户当前明确表达确立业务意图，`context/` 保存已知业务规则，代码提供实现现状。

## 每轮执行

1. **先读。** 开始分析业务前，读取 `context/index.md` 及匹配主题。使用当前话题中的业务词汇匹配索引；涉及跨领域关系时读取两端主题。当前上下文中的已读内容直接复用，恢复上下文后重读相关主题。
2. **提炼。** 检查本轮用户表达及调查结果，找出新增、修订或尚待明确的业务含义。把功能诉求还原为规则：谁在什么条件下，可以对什么对象做什么，结果如何影响身份、归属、关系或后续生命周期。
3. **立即处理。** 在下一次对用户输出前，将明确且有记录价值的规则写入对应主题；把影响业务判断的歧义整理为该次输出中的具体问题。确定部分先写，待定部分留在当前对话。用户明确修订时同步替换旧规则。
4. **核对完成。** 本轮每条有价值的明确规则都已落实到主题正文，索引能通过对应业务词汇找到它；待定规则已有具体问题。已有条目完整表达本轮含义时直接复用。完成这些动作后继续当前工作。

## 挖掘什么

保存项目特有、能指导后续业务判断的知识。问自己：**另一个 agent 知道这条事实后，会怎样改变对业务的实现？** 能指出具体影响，就提炼其业务含义。

从当前话题中追踪这些线索：

- 身份：如何识别同一个业务对象，编号在哪个范围唯一，何时产生或改变。
- 关系：对象属于谁，双方数量关系如何，哪些对象独立存在。
- 生命周期：什么使对象进入下一状态，撤销或重做会改变哪些业务结果。
- 约束：谁在什么条件下具备操作资格，哪些例外改变规则。

选择当前表达涉及的维度继续推敲，用具体场景询问会改变结果的分歧。将“这个字段或分支现在如何实现”进一步转成“业务为什么允许这种情况”。实现证据用于发现问题，用户明确表达与回答用于确立意图。已实现规则的业务含义同样值得保存。

每条事实用最短的完整业务表述写清，包含必要的适用范围与例外。持续合并重复含义，替换被修订的事实，使主题正文始终表达当前有效知识。

## 文件与索引

```text
context/
  index.md
  <业务主题>.md
```

在项目根目录查找该入口。第一条有效事实出现时创建所需文件，按实际业务领域拆分主题。索引每个主题一行：主题链接，以及用户使用的业务词汇和已知别称。主题内用简短标题聚合规则；事实集中在一处，相关主题通过链接引用。

业务规则写入主题正文，技术现状通过代码查询，讨论过程留在会话。

## 协作

日常主动检索的业务与实现材料限于代码和 `context/`。当前上下文明确提供或正在使用的临时材料按需重读，续接中保留的路径同样适用。历史文档在用户明确指定临时审查时读取，并在该审查中比较文档与实现。技能指令和项目操作规则按各自适用范围读取。

复杂功能包含值得用户提前了解的行为或取舍，且用户表达实现意愿或明确要求说明时，先在对话中简述结果、关键行为和取舍。用户已要求实现时，说明后继续执行。相关实现依赖业务答案时先解决该问题，其余已授权工作继续推进。

与 matt-pocock 技能组合时，由对应技能组织访谈、规划和评审，本技能同步完成每轮业务知识维护。领域词汇表的读写统一映射到 `context/` 的索引及主题文件；业务术语随其规则保存。
