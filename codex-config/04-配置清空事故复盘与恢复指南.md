## 侦探式破案：为什么抓个包会清空配置？

很多人的第一反应是：“是不是抓包工具带毒，偷偷删了配置？”或者“是不是官方自动升级重置了配置？”  
通过深入排查进程、日志与代码调用链，真正的元凶浮出水面——**双实例资源抢占引发的连锁冲突**：

```
           正常使用的 Codex 实例 (PID: 49992 / 88792)
                              │
                              ├────────► 共同读写同一个 ~/.codex/config.toml ！！
                              │          共同争抢同一个 ~/.codex/.sandbox-bin 锁 ！！
                              │
           抓包工具双开的第二实例 (PID: 22428)
           (带 --proxy-server 代理参数)
```

### 致命漏洞：只隔离了桌面 Profile，没隔离 `CODEX_HOME`！

1. 抓包工具在启动第二个 Codex 桌面实例时，只设置了 `--user-data-dir`（桌面的网页缓存目录）。
2. **但是，它完全没有隔离 `CODEX_HOME` 环境变量！**
3. 这导致后台的第二实例与正常正在使用的主实例，**同时指向了同一个 `C:/Users/stoneedle/.codex/` 后端配置目录**。

### 灾难发生的链条：
1. **17:30~17:34**：双开的抓包实例与主实例几乎在同一时刻发起 `windowsSandbox/setupStart`（沙箱初始化）。
2. **发生锁死**：系统写入错误日志 `helper_sandbox_lock_failed`——无法同时打开并锁定共享的 `.sandbox-bin` 目录。
3. **精简配置意外回写**：双实例在并发抢占配置目录与沙箱锁期间，处于临时精简环境的抓包实例在退出或状态同步时，将其简化的内存配置覆盖写入了共享的 `config.toml`，将主实例原有的丰富配置洗刷清空！
4. **抓包实例未正常退出**：调试结束后，抓包代理服务已经关闭，但抓包实例（PID 22428）依然在后台残留运行，导致网络连接一直处于半瘫痪状态。

## 惨痛教训与防灾避坑守则

为了确保悲剧不再重演，请严格遵守以下三大保命原则：

### 原则一：动配置前，先执行一行命令备份
无论何时准备编辑 `config.toml`，在终端里敲一下这行命令，只需 1 秒钟：

```powershell
# 一键备份 Codex 配置
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
Copy-Item "$env:USERPROFILE\.codex\config.toml" "$env:USERPROFILE\.codex\config.toml.bak-$stamp"
```

### 原则二：抓包与调试多实例时，必须隔离 `CODEX_HOME`
如果以后需要启动第二个 Codex 实例进行抓包、测试：
**必须指定独立的 `CODEX_HOME`**，让它使用独立的配置文件夹，绝对不能与日常主力配置共用！

```powershell
# 安全启动测试实例示例
$env:CODEX_HOME = "$env:TEMP\codex-test-home"
# 再启动你的测试程序
```

### 原则三：抓包结束后的收尾流程
每次抓包排查完毕：
1. **先关客户端**：先关闭依赖代理的 Codex 窗口；
2. **再停代理服务**：最后停止抓包代理工具；
3. 检查任务管理器，确认没有残留的无头进程挂死在后台。
