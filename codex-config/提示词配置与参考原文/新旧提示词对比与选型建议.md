# 新旧提示词对比与选型建议：为什么旧版总爱反复问你？

> **一句话导读**：很多老用户觉得新版 Codex（GPT-6 Astra）好像变聪明了、干活更顺手了，但又有些怀念以前自己定制的提示词（GPT-5.5 时代）。  
> 本文深度对比两版提示词的差异，彻底揭秘**“为什么旧版提示词动不动就停工反复找你确认”**的深层逻辑，并给出兼顾两者优点的最佳选型策略。

---

## 两份提示词的规格概况

| 对比维度 | 旧版共享提示词 (GPT-5.5 时代) | 新版官方提示词 (GPT-6 Astra 实测抓包) |
| :--- | :--- | :--- |
| **字符规模** | 约 10,990 字符 | **约 21,420 字符**（接近旧版 2 倍） |
| **整体基调** | 防守型、强约束、工程规范浓厚 | 自治推进、结果导向、工具与生态成熟 |
| **人格风格** | 早期带有一些拟人化偏好，后精简为极简协作 | 专业、克制、严谨、直接的工程 Agent |

---

## 核心差异深度剖析

### 1. 为什么旧版总喜欢反复问你？（最关键的体验差距）

* **旧版的“审批铁笼”**：  
  在旧版的 `Sensemaking And Design`（理解与设计）章节中，明确规定了苛刻的审批条款：  
  > *“只要下一步改动涉及架构、API 接口、数据持久化、数据模型、外部集成、UI 工作流中的任何一项，就必须要求具体设计获得批准；存在多个合理实现时，必须等待用户明确批准。”*
  
  **这就形成了一个巨大的死循环**：在软件开发中，几乎任何一行稍微有价值的代码都会涉及 API、数据结构或流程！再加上一条“有多种合理实现就必须等待批准”，导致模型哪怕只是想写个工具函数、建个表单字段，都会立刻踩中煞车，停下来弹出对话问你：“我这里有方案 A 和方案 B，你同意我这样改吗？”  
  这直接摧毁了“全自动 Coding Agent”的连续性体验。

* **新版的“自主闭环”**：  
  新版 Astra 基础指令彻底推翻了这一死板设计，重构为以**“已有授权 + 可逆性 + 任务范围”**为核心的心智模式：
  > 只要改动是可逆的、在已有任务上下文授权范围内的，模型将自主评估最佳方案并直接落地编码；只有遇到难以逆转（如删库、大范围破坏性重构）且现有证据无法决定的核心分歧时，才主动停下来询问。

---

### 2. 任务推进的心态差异

* **旧版**：强调低风险才能实施，信息稍微不够清晰就倾向于停工找人对齐。
* **新版**：将用户的“帮我做…”、“能不能搞一下…”、“我想…”直接当作强力行动指令；即使信息不全，也会自主把确定独立的模块先行落地，再就未知部分发起精准询问。

---

### 3. 工程架构与代码偏好

* **旧版的闪光点**：  
  旧版其实包含很多极其优秀的资深工程师偏好：
  * **深模块与窄接口**（Deep Modules, Narrow Interfaces）；
  * **单一事实源**（Single Source of Truth）；
  * **零冗余兼容**：坚决不留死代码，重构新实现时必须同步删除旧代码；
  * **测试约束**：不写无意义的废测试（如只断言文件是否存在等）。
* **新版的不足**：  
  新版官方提示词将大部分篇幅留给了工具操作、PR 输出格式规范、网络协作等通用能力，对于团队特定的架构偏好提及较少。

---

### 4. 工具与生态适配

* **旧版**：还停留在旧式 `multi_tool_use.parallel` 工具调用规范，缺乏对现代 Promise 并行机制、插件体系（Plugins/Apps）和技能渐进加载的完整指导。
* **新版**：全面适配现行底层工具栈（如 `functions.exec`、结构化并发、权限边界）。如果拿旧版完全替换新版，会导致很多现代工具调用能力失效。

---

## 终极选型建议：博采众长的最佳实践

> [!TIP]
> **绝对不要整份换回旧版提示词！**  
> 盲目整份替换不仅会丢失新版的工具生态能力，还会重新把你拖入“每写两行代码就被问一次”的痛苦深渊。

### 最优组合方案：官方新版做底座 + 旧版工程精华做追加

1. **以新版 Astra 为底座（保持默认）**：  
   让官方内置的约 2.1 万字符指令负责底层的工具编排、自治推进、PR 格式和基础行为。
2. **提取旧版精华，作为 `developer_instructions` 注入**：  
   在你的 `config.toml` 中，把旧版真正有价值的架构规范提炼出来进行追加：

```toml
developer_instructions = '''
# 团队核心工程原则 (继承旧版精华)

1. 架构设计：
   - 坚持深模块、窄接口设计原则，内部实现细节高度封装，对外暴露极简 API。
   - 坚持单一事实源（Single Source of Truth），拒绝多处维护相同定义。

2. 兼容与重构：
   - 坚决杜绝无意义的旧实现残留。替换重构时，同步彻底删除被取代的废弃代码与冗余兼容层。

3. 测试策略：
   - 仅针对核心业务逻辑与边界条件编写高质量测试，杜绝为了覆盖率而写无意义的纯文件存在性断言。

4. 自主推进：
   - 保持新版的自主闭环特性。对于低风险、可逆改动自主落地；仅当涉及不可逆重大决策且缺乏依据时才请求确认。
'''
```

通过这种配置，你既能拥有 GPT-6 Astra 的丝滑自主编码体验，又能让它写出符合顶级架构规范的干净代码！
