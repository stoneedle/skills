# Codex 请求剖析与 Token 消耗揭秘

> **一句话导读**：你在输入框里只打了一个字 `hi`，但 Codex 发往模型的请求体里却默默塞进了 **24,486 个 Tokens**！  
> 这近 2.5 万个 tokens 到底包含什么？系统提示词真如大家所想的那样工作吗？本文基于真实网络层抓包，为你彻底拆解 Codex 的底层通信秘密。

---

## 震撼的数据：一次最简单的对话开销

在针对真实的 Codex 桌面版（模型 `gpt-6-astra`）的网络抓包实测中，我们记录到了发送一句最简单的 `hi` 时的真实输入上下文开销：

```
你的提问： "hi"  (仅 6 Tokens)
  │
  ▼
Codex 发送给模型的总上下文： 24,486 Tokens !
```

用户输入的真实内容只占了总开销的 **0.02%**，剩下的 **99.98%** 全是 Codex 运行环境为了支撑大模型像程序员一样工作而装配的“重型装备”。

## 协议层真相：三大颠覆认知的发现

### 发现一：请求里根本没有 `role = "system"`！
很多初学者甚至 AI 工程师都以为 Codex 会向 OpenAI 发送一个经典的 `system` 角色消息作为 System Prompt。

但通过真实抓包解码发现：
* **`system_message_count = 0`**；
* 客户端外发的所有系统基石指令、工具列表、技能清单、权限说明，全都统一被装在 **`role = "developer"`** 类型的消息块中；
* 项目规范、环境上下文与用户提问则被归在 **`role = "user"`** 消息块中。
（注：抓包展示的是客户端向服务端推送的完整报文；服务端内部隐藏逻辑不在此抓包边界内。）

### 发现二：技能是“常驻元数据 + 按需加载正文”
很多开发者担心：“我本地装了 50 个技能，每个技能几千字，是不是一次就把几十万上下文撑爆了？”

**真实机制是两段式的**：
1. **常驻目录（Catalog）**：Codex 启动后，会扫描所有技能目录，把所有技能的 `name`（名称）和 `description`（描述）拼装成一个清单，**塞进每一个请求的 developer 消息里**（上面的 4,650 tokens 消耗就在这里）。
2. **按需读正文（Content）**：每个技能的 `SKILL.md` 正文、参考代码，在初次提问时**完全不会预先加载**！只有当模型读了技能描述，判断当前任务必须调用该技能（或用户在对话中显式引用）时，模型才会主动触发工具去读 `SKILL.md` 正文。

> [!TIP]
> **技能编写的核心心智**：  
> 技能的 `description` 越长，每次请求常驻目录占用的上下文就越多！虽然现代大模型支持 Prompt 缓存，但在初次加载或缓存失效时依然是直接的开销。因此写技能时，`description` 务必高度概括（仅说明“在什么情况下使用本技能”），把几十页的技术细节通通放进 `SKILL.md` 正文或外部 Markdown 里。

### 发现三：工具定义占据了将近半壁江山
工具定义占了 **11,478 tokens（接近 47%）**。  
为什么工具定义这么占地方？因为现代 Agent 需要极为严格的结构化入参约束。每个工具的每个参数类型、必填项、详细的描述解释全部转成了 JSON Schema 发送给大模型。这是 Agent 能够准确调用命令行、编辑代码的核心基础，属于必要的系统开销。

## 如何给 Codex 上下文“科学瘦身”？

理解了上面的账单结构，优化上下文开销就不再是盲人摸象：

1. **清理和禁用不需要的技能**：
   实测中，49 个技能吃掉了 4,650 tokens，平均每个技能吃掉近 100 tokens。如果你项目里堆积了大量陈旧的、未使用的技能，或者同名技能被重复扫描（见下一篇），通过配置禁用它们可以直接砍掉数千 tokens 的常驻包袱。

2. **精简个人和项目的 `AGENTS.md`**：
   不要在 `AGENTS.md` 里写长篇技术文档。只保留最重要的 3~5 条规则（如包管理器选 pnpm、必须写单测、API 规范等）。

3. **避免在提示词中重复定义工具**：
   既然系统已经自动注入了 11,500 tokens 的工具声明，就不要在自己的 `developer_instructions` 里反复教模型“你有 exec 工具、你可以跑命令”，这完全是冗余的。
